01 — The Problem

Why do we need RAG?

🧠
Stale knowledgeBase models don't know our internal docs — they guess, and guess wrong.
🔒
Data privacySending proprietary internal docs to a third-party API is a data exposure risk.
📚
Context limitsContext windows can't hold hundreds of pages of documentation at once.

02 — The Concept

What is RAG?

🔎 Retrievalfind the relevant facts
+
🧷 Augmentedinject it as context
+
✍️ Generationanswer using that context
From "guessing from memory" to an "open-book exam." The model isn't smarter — it just isn't guessing anymore.

03 — Conceptual Flow

Two phases, two different times

Phase 1 — Ingestion (background, ahead of time)
📄 Internal DocumentsPDF / MD
→
✂️ Word Chunking
→
🗄️ Vector Databaseknowledge base
Phase 2 — Querying (runtime, every question)
❓ User Question
→
🔎 Vector DB Search
→
🎯 Top Matching Chunks
→
🤖 LLM + Context Prompt
→
✅ Precise Sourced Answer

The LLM only ever appears in phase 2 — and only ever sees the handful of chunks retrieval already picked out.

07 — Engineering Highlights

Built to be practical, not just possible

⏱️
Incremental ingestionEach file's ETag is tracked in .ingestion_state.json — re-running only touches new or changed files.
🔌
Zero-code-change portabilityMinIO ↔ AWS S3 is an .env change, not a code change. Same codebase, local dev today, production tomorrow.
🪶
Lightweight footprint~6 GB total disk. Runs on a standard CPU — no GPU required anywhere in the pipeline.
